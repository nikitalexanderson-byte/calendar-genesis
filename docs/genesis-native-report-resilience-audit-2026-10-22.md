# G4/C6/U: аудит устойчивости нативного отчёта

Следующий локальный срез после `3589523`: один существующий экран `SharedSprintReportScreen`, без деплоя, нового публичного APK, SSH и телефонов. Общий статус 11/32 +21 частичный ID и14 K/U/L сохраняется.

`SprintReportState.refresh(nextUnit)` заранее убирает report и сохраняет fallback только для совпадающей единицы. При NETWORK во время смены единицы подтверждённая сводка теряется; `goOffline()` во время ожидающего refresh также видит только null. После ошибки источников selection сбрасывается, но pane остаётся sources. В `SharedSprintReportScreen` отсутствует существующий в командном отчёте listener потери сети. Это проверяемые гипотезы по исходникам, до baseline не объявленные подтверждёнными failures.

План: проверить эти переходы focused state/UI-тестами до правки, затем хранить только последний подтверждённый aggregate в памяти на время refresh. При NETWORK восстановить его исходную единицу, удалить token/sources/task, вернуть обзор из источников и ждать явного Refresh. Реальный отзыв прав, изменение отчёта и disposal должны очищать fallback и отвергать поздний ответ. Холодный offline не создаёт сводку. Сеть подключить через уже используемый ConnectivityManager, не вводя другую инфраструктуру.

UX-срез ограничен этим экраном: выбор новой единицы недоступен в offline, Refresh доступен; события/изменения/события дня — общие AffairsIconButton 48dp/10dp с локализованными доступными именами. Метрики сохраняют числа; overview/charts/data остаются смысловыми блоками. Названия статусов и задач уже используют прямой Material Text; это требуется подтвердить без новой подстановки. Проверить обе темы ×360/390/768/1440dp, font1,3,14 языков на мобильном размере, до/после PNG, текущий build/lint и весь существующий sprint-report regression. Физические устройства, Google OAuth, production HTTP, TalkBack и release-приёмка в этот узкий срез не входят.

Baseline state-прогона подтверждён:30 JUnit cases,3 ожидаемых failures — потерянный aggregate при смене единицы, потеря во время pending refresh и неверный pane после сетевой ошибки источников. После state-исправления31 focused cases прошёл, включая новое очищение fallback/late reply при close/revoked/REPORT_CHANGED. Первоначальный after JUnit использовал старый Gradle runtime JAR; это устранено в harness загрузкой текущих compiled Kotlin/Javac classes с SHA-256, без объявления Gradle worker исправленным.

Первый UiDevice.takeScreenshot захват дал обрезанный справа кадр на wm override.16 таких PNG не принимаются как полная визуальная проверка. Для исправленного before используется APK из изолированного QA package с хешем, совпадающим с ранее DEX-проверенным baseline; тестовый APK новый, но продуктовый остаётся3589523. Новый захват использует физический screencap и metrics. Ошибки дополнительных stdout-проверок capture-harness и отсутствующего префикса originals в тестовом asset path учитываются отдельно от продуктовых failures.

Офлайн-сообщение использует существующий локализованный network copy один раз, без ложного утверждения об изменении доступа. «Состав и оценки» открывается иконкой просмотра, а события — иконкой истории; подписи метрик остаются числовыми.

На физическом before-confirmed screencap найдены белые системные status-иконки на светлой поверхности и тёмные navigation-иконки на тёмной. В окно перенесён существующий из SharedTeamReportScreen SideEffect с WindowInsetsControllerCompat; финальные кадры должны подтвердить оба случая. API35 gateway regression прошёл13/13 с3 opt-in skips на APK до этого изменения. Opt-in реального сетевого отключения API35 пока не принят: после отключения Wi-Fi/data глобальная default network отсутствует, но на настоящем снимке остаются sources100/131; три запуска завершились timeout ожидаемого offline-состояния. Сетевые settings1/1 восстановлены в каждом протоколе. Добавлены минимальные flags activeNetwork/capabilities/видимых узлов для различения ошибки приложения и предположения harness; до диагностики окончательная причина не заявляется. Первый peek-helper из-за replace только первого вхождения сделал кадр5554 под именем API35; этот кадр не принят. На сборке075414ed диагностический реальный disconnect API35 прошёл: active Wi-Fi103→null, sources скрыты, offline aggregate остался, после подключения104 auto-refresh не выполнен. Нужны повторные прогоны на конечной сборке.

Первый after-bars360dp просмотрен: системные панели теперь контрастны в обеих схемах; иконки компактны и48dp. Обнаружена новая UX-проблема: Material disabled alpha делает офлайн-числа и выбранную единицу слишком бледными. Для этих данных выбран существующий onSurfaceVariant с сохранением disabled semantics. Полный after-bars instrumentation прошёл4/4 ширины,136 PNG:14 языков на390dp, поEN на360/768/1440dp, font1,3, обе схемы. Display settings восстановлены. Ошибки/offline status получили polite live-region; реальный TalkBack этим не объявляется проверенным.

При проверке последнего offline-состояния обнаружено, что private ReportChoice хранил expanded независимо от enabled: открытый список единиц мог остаться доступным после блокировки селектора. Добавлено закрытие по enabled и выключение пунктов. Opt-in реального отключения сети теперь открывает меню заранее и проверяет его отсутствие после offline; diagnostics включает unitMenuNode. Это дополнение ещё требует конечного запуска, не объявлено отдельным baseline PASS. Краткая ошибочная вставка открытия меню в соседний тест131 строк исправлена сразу по контексту метода до приёмки; этот промежуточный файл не принят как продуктовый дефект.

Конечный callback-only прогон с открытым меню на efeed952 снова завершился timeout: activeNetwork104→null, но sources/unitMenu оставались видимыми; settings1/1 восстановлены. Один прежний диагностический PASS не подменяет этот failure. Для надёжного обнаружения разрыва добавлен lifecycle-scoped Handler main-loop monitor1s и основной callback переведён на тот же main Handler. Проверяются только локальные ConnectivityManager/state; при доступной сети refresh не запускается, в фоне monitor останавливается. Handler удаляет только собственные сообщения при dispose. Нужны новая сборка, оба SDK и повторные реальные disconnects с открытым меню.
