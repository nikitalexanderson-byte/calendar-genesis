# G4: аудит источников и решение перед реализацией

Основание: master71da6c7 с G3 server/web; ветка `codex/genesis-sprint-flow-reports`. Это аудит следующего этапа, без реализованного G4 API или графиков. Требование G4 остаётся открытым. Актуальный список основного остатка — `genesis-remaining-work-2026-10-18.md`.

Источники уже существуют. `genesisPlanningTaskState()` в `server/src/shared-planning.php` сохраняет taskId, statusId, done/active, revision, assigneeId, sprintId и независимые оценки. `sprint.started` и `sprint.completed` сохраняют зашифрованные plan/outcomes и точный observedAt в существующем audit. Task-события C4 имеют внутренний reportState с состоянием статуса и planning. Для первой реализации отдельная параллельная история задач или миграция пока не обоснованы.

`genesisPlanningSafeDetails()` удаляет недоступные задачи из исторических планов, а reportState намеренно не отдаётся через обычную activity UI. Новый отчёт должен применять текущие права проекта и `genesisSharedReadableReference()` перед раскрытием task IDs/оценок; названия получать только из разрешённого текущего источника. Отчётные token/fingerprint/пагинация должны сохранять правила C4. Потеря доступа после построения не должна позволять дочитать сохранённый drill-down или восстановить скрытые суммы.

Начальная точка спринта — реальный `sprint.started.plan`, а не сегодняшний snapshot. Планируемые startDate/endDate и фактические startedAt/completedAt различаются: запуск сегодня не создаёт историю задним числом в прошлом запланированном периоде. Дни группируются в сохранённом часовом поясе и календарном контексте. Смена вида календаря не меняет сохранённую длительность. Задачи, уже завершённые к запуску, показываются отдельно от выполненного за спринт объёма.

Важный край завершения: `genesisSharedTransitionSprint()` получает plan до carry-over, затем меняет sprintId незавершённых задач и лишь после этого пишет `sprint.completed`. Нельзя принять служебные исходящие carry-события за выполненную работу и нарисовать нулевой остаток. Пример приёмки:10 задач,4 завершены,6 перенесены — факт4, остаток на закрытии6 и явный перенос6. Terminal plan содержит состояние до carry-over; outcomes/revision позволяют отличать эти изменения от обычного удаления scope даже при одинаковом timestamp. CFD по проекту и CFD выбранного спринта должны явно различать свою область.

Агрегатор должен воспроизводить реальные изменения: вход/выход из спринта, добавление/удаление/архив/восстановление задачи, оценку, статус, reopen и перенос между проектами. Для каждой точки хранить источник eventId/sequence и причины изменения scope. Points, часы и количество задач — отдельные единицы.0 является оценкой, null — «не оценено». Суммы points ограничены одним проектом/шкалой, исходная единица спринта заморожена при запуске. Изменение оценки завершённой задачи не должно создавать дополнительное завершение.

Пропуски до первого достоверного наблюдения, события старого сервера без reportState, прыжки revision и повреждённые timestamps означают unknown/partial, а не нулевую работу или прямую линию от нынешнего snapshot. У каждого показателя нужны покрытие, количество неизвестных/неоценённых задач и разрешённая исходная выборка. События C5 исторического импорта не превращаются в новые живые события производительности: `GenesisDataHistoricalScope` намеренно исключён из audit hook. Импортированные sidecars остаются историческими метаданными.

Предлагаемый первый срез — чистый серверный fold существующих событий, read API в одном проекте и дополнение текущего окна планирования. Метрики: фиксированный стартовый план; факт и остаток на закрытии; добавленный/удалённый scope и изменение оценок; burndown с разрывами покрытия; CFD и WIP; отдельные исходные события/задачи. Для завершённого спринта terminal plan служит проверяемой опорной точкой. Ограничения периода, согласованный read snapshot и cursor/fingerprint нужны до графиков.

Обязательные проверки перед UI:0/null; добавление/выход/оценка после запуска; выполнение/reopen; архив/trash/restore; смена проекта/прав; задачи больше100; одинаковые timestamps и последовательность; completion/carry-over без ложного нуля; старый сервер и пропуски; календарные границы/часовой пояс; C1/C2/C5/B-интеграции; соответствие метрики её исходным строкам. Затем14 языков, две темы×360/390/768/1440, browser drill-down/refresh/revoke и native-приёмка. Этот аудит не закрывает ни G4, ни общие K/U/L.
