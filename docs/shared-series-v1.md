# Shared task series and background work

This stage extends the existing PHP cron. It creates no browser timer or new service stack. Series are authored by an organizer with current write permission; every worker attempt rechecks that actor and the destination project.

An existing saved task is the first instance. Scheduled instances are materialized on their civil due day in the rule's saved IANA zone, including catch-up after downtime. At most five instances of one series and twenty tasks in one template tree are processed per batch. A visible total limit (1–1000 including the initial instance and skips) bounds a series. Pausing holds the cursor; resuming catches up. Excluded dates are durable skips. Explicitly skipping an open instance archives its tree and retains its identity and history. For an after-completion series, that skip advances the chain from the original occurrence date.

After-completion series wait for actual completed_at (including final approval), then add a civil interval in their saved calendar. Reopening before generation cancels eligibility. Once a successor exists, reopening/reapproving the predecessor never makes another. A moved due date affects only that instance. Moving an instance to another project does not move the series or grant access to it.

Each instance has a stable series/key mapping. Existing task revisions, mutation receipts, encryption, completion/approval guards and audit remain authoritative. A series edit changes only instances not yet materialized; edited or already generated instances and their histories are never deleted or overwritten. Changing future content explicitly snapshots the currently saved source task/tree. New checklist IDs and unchecked items are created; internal parent, dependency and checklist-child links are remapped. Assignees and approvers must still be available. Comments, files, images and external dependencies are not copied, and the preview explains that policy.

Background jobs have durable unique keys, leases, bounded attempts/backoff and redacted diagnostic codes. A handler commits its data and completion acknowledgement together; expired leases retry the same operation up to five attempts. Series revisions cancel stale pending jobs, and errors from old revisions cannot mark an edited series. The scanner rotates every inspected row, including waiting and future series, to prevent starvation after the first 100 rows. Waiting after-completion series consume no job key; completing later on the same day can enqueue immediately. Jobs do not create external messages or subscriptions. Future automation actions must reuse the same series/instance identity when generating the same successor.

Relative dates for children and checklist items shift with the occurrence. A new shifted date outside 1900–2100 rejects the entire generation transaction; saved historical dates remain unchanged. Existing task edits never rewrite the stored series template without the explicit refresh option.

Migration is additive (059); runtime backup is provided by the existing deployment workflow before application migration. A code revert preserves series/instance/job tables and existing generated tasks. Database restoration is never automatic.
