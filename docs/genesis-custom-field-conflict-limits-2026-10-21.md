# C3: конфликт версии и предел вариантов

Аудит продолжения4514ad1 подтвердил два остатка. Web после первого документированного revision conflict предлагает editing с прежним expectedRevision, поэтому следующий preview повторяет409. Server проверяет200 только во входном options, а затем добавляет исчезнувшие старые варианты как archived; нормализованный ответ может оказаться201+, который прежний native/браузерный durable reader отвергает.

Решение для существующего экрана управления полями: отдельное явное обновление базы при сохранении собственного ввода; неизвестный уже отправленный PUT нельзя переводить в editing. Новый preview и подтверждение обязательны. Ошибки загрузки текущей версии сохраняют ввод. Кнопки используют общие icon/short action styles.

Для обычных новых/существующих полей общий предел200 проверяется после возвращения archived вариантов. Прежние201+ определения сохраняются как совместимый read/edit случай: не более200 действующих вариантов, без увеличения прежнего общего количества и без удаления старых IDs/значений. На стороне клиента используется существующая ограниченная transport/journal byte envelope вместо неверного200 total для чтения истории. Явные JSON/template read paths сохраняют archived metadata в прежних bounded envelopes; транзакционный C5 historical scope может временно разархивировать варианты только до восстановления прежних значений и возврата исходных flags перед commit. Публичный API такого флага не принимает. UI не разрешает добавление новых вариантов сверх предела. Превышение объясняется локализованным сообщением; миграция и production SQL не нужны.
