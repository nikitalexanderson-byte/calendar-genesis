# G1: формы и действия планирования после перезагрузки

Продолжение после PR #205. Срез сохраняет незавершённую новую/редактируемую форму спринта, решения о переносе незавершённых задач и точные неподтверждённые команды settings/create/edit/start/complete. Оценки в отдельных строках G2 пока остаются отдельным остатком. Для G1 и опубликованного G3 дополнительно сохранена идентичность неподтверждённого запроса при ошибке storage и отказе ACL на повторе.

## Поведение

В окне планирования появился каталог локальных черновиков с временем записи, явным продолжением/удалением и отдельной отметкой неподтверждённой отправки. Закрытие, reload и cold offline сохраняют форму. Редактировать восстановленный текст можно без сети; отправка требует свежего серверного read и текущих прав. Восстановление и подключение не выполняют автоматических изменяющих запросов.

До первого изменяющего запроса journal подтверждает сохранение точных requestId, body, expectedRevision и fingerprint. Потерянный committed response повторяется с тем же UUID и телом; server receipts возвращают прежний результат. Определённый4xx первой отправки оставляет правку доступной для исправления. Ошибка crypto/storage до первой отправки не объявляется неподтверждённой серверной отправкой и не блокирует редактирование. Если предыдущая попытка уже не подтверждена, новый storage/ACL отказ не снимает неопределённость: исходные UUID и тело сохраняются до подтверждения либо отдельного явного удаления локальной копии. Это исправлено и в G3 SharedWorkflow, поскольку сервер проверяет текущие права до чтения receipt. После получения ответа фоновой странице проекта больше не нужно завершать своё обновление, чтобы разблокировать окно планирования.

Каждая вкладка имеет свой writer. Восстановление не перезаписывает исходник другой вкладки. CAS при очистке сохраняет изменившуюся исходную копию и сообщает об этом. Повреждённый/неподдерживаемый документ можно скачать без изменения его байтов и удалить отдельно. Quota оставляет прежнюю сохранённую копию и текущий текст. Используются существующие лимиты journal:20 записей на scope и2000000 UTF-8 bytes на payload; browser quota может быть меньше.

Форма хранит исходные ISO dates и CalendarContext v2, включая timeZone и начало григорианского года; восстановление не пересчитывает даты и не меняет календарь ввода. Редактирование существующего спринта с новой revision требует явного обновления базы при сохранении введённого текста.

## Задачи и права

В completion journal находятся только task IDs/revisions и выбранные назначения. Task titles/values, участники, отчёты и cached permissions не записываются. После восстановления названия скрыты до свежей полной выборки всех страниц. Дополнительный planning read после списка проверяет текущие права и тот же fingerprint. При изменении состава названия снова скрываются; явное обновление сохраняет только решения для прежних task revisions и доступных целей. Изменившаяся задача требует нового выбора.

GET planning аддитивно возвращает только три уже вычисленных authoritative permissions: editTasks,organizeTasks,manageProjects. Клиент перестал брать разрешение на изменение из родительского snapshot. Серверные write guards, receipts и atomic lifecycle не меняются. Фоновые planning reads больше не накладываются друг на друга: ответ медленнее5s не должен бесконечно отклоняться очередным poll.
