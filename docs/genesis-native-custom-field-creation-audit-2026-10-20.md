# C3: пользовательские поля при создании общей задачи в Android

Следующий экран после PR #226 — существующий диалог «Новая задача команды». Project snapshot уже содержит определения; только что завершённая native карточка даёт семь controls, валидацию, archived/unavailable recovery и независимый input calendar. Создание пока передаёт только title/description/date/status/category/assignee. Для проекта с обязательными полями это оставляет человеку непонятное серверное отклонение без возможности заполнить поле.

Предлагается переиспользовать controls внутри текущего диалога, показать required сразу после названия, optional под единым disclosure. Сохранить существующие календарь срока и остальные действия; собственный календарь пользовательских дат инициализировать из UiPreferences.input. Локальный draft должен быть привязан к проекту и аккаунтному composition scope, переживать recreation, не утекать в другой проект и очищаться только после подтверждённой передачи либо надёжного enqueue. При серверной ошибке оставлять весь ввод в форме.

Для нового task base — известная пустая value map; null/false/zero различаются. В create body включаются только введённые custom IDs, без synthetic task identity и editor metadata. Использовать существующий AuthController.createSharedTask и encrypted task outbox. Его receipt уже подтверждает custom patch; requestId/неопределённый результат/последующий retry не переписываются. Отдельный sourceTaskId-copy маршрут не расширять этим экраном.

Права создания на сервере соответствуют существующему write/editTasks; нового permission createTasks нет. Учитывать актуальные permissions, архив проекта, busy и актуальный catalog. Изменение определения/обязательности во время ввода не должно терять свой текст или молча принимать недействующий archived option. Отклонение C3 должно быть видно внутри открытого диалога; общая feedback под закрытым modal недостаточна.

До UI-изменения сохранить исходный диалог в обеих схемах на360/390/768/1440. Проверить new-task required/false/0/date/select/multi, серверное отклонение и исправление, recreation/смену проекта, permissions, cold queue/неполный receipt и прежнее создание без полей. Реальный loopback create/replay должен вернуть одну задачу и удаляться только через synthetic API fixture. Затем одна initial/confirm visual matrix, i18n, обязательные frozen install/lint/test/build и release compile по необходимости после изменения большого Compose-экрана.

Этот экран не закрывает C3 definitions/history/list visibility/filter/sort, другие C/G/B-интеграции, signed/device/Google и общую приёмку. Остаток —21 частичный ID и14 K/U/L. Новых миграций и production DB edits не требуется; SSH не используется.

Реализованы scoped/saveable create state и повторное использование task controls. Scope открытого диалога хранится независимо от временного projectId загрузчика, чтобы recreation не стирало форму. Непереносимый/малформированный saved record даёт boundary и требует явного reset. Проверяется соответствие последнего ввода render binding перед формированием тела; серверная ошибка остаётся в фиксированном заголовке открытого окна. Роль/permissions editTasks и архив учитываются до create. Успешный receipt или защищённый enqueue очищают форму; после отказа она сохраняется.

Полный JVM-набор —496 tests без failures/errors/skips, включая реальное PHP create/replay: required,0/false, все семь типов, недоступный архивный вариант, неправильный wire number, одна запись после потерянного ответа и soft-trash только созданного synthetic task. На API28 и API35 прошли33 выполненных workspace/store сценария; пять capture-only entries отдельно пропущены. После последней правки на каждой API подтверждены ещё9 целевых сценариев, включая два новых cases отключённых сакральных функций, refresh при отказе, explicit-clear validation и три input calendars. Это35 разных выполненных cases с учётом объединения, не40 из строки runner с skips.

Валидный baseline диалога —8 снимков обеих схем/четырёх ширин, initial76 и confirm88 native originals. Подтверждены360/390/768/1440, font130,14 языков (invalid form), required/ready/rejected/invalid/optional/calendar; дополнительные12 confirming кадров — режим без сакральных функций. Пустые required inputs нейтральны до ввода/явной очистки, actual binding всё время блокирует неполное создание. Рядом с видимым отказом есть общая refresh-иконка с tooltip. При выключенных сакральных функциях нет пустого выбора календаря; read-only даты показываются Gregorian ISO, а исходный input mode и значения сохраняются.

Debug/test и unsigned release/R8/lintVital прошли; последний build1m38s, APK SHA2564a9c82b377f8d07ac3c348824785f10368f150c03938ea9207ca084f1bd53e6f. Нового публичного Android-выпуска этот срез не создаёт.
