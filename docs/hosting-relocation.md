# Подготовка переноса GENESIS на другой хостинг и домен

Целевой адрес — `https://genesiscalendar.com`, Hostinger. Источник кода — `nikitalexanderson-byte/calendar-genesis`. Новый закрытый корень: `/home/u531952483/domains/genesiscalendar.com`; публичен только `public_html`. На Beget разрешён только прежний корень `/home/h/haiirodw/genesis-calendar`.

## Условия перехода 8 октября 2026

- На новом адресе доступен только вход Google. В закрытой конфигурации `google_only=true`; параметры Яндекса не переносятся. API Яндекса возвращает 404, кнопки входа и подключения скрыты, Метрика не загружается. Исторические данные не удаляются.
- Пакет Android `ru.genesis.calendar`, действующая подпись и тестовый трек сохраняются. Новая сборка 2.6.7 / 73 использует новый origin; локальный контекст шифрования авторизации уже независим от домена. Не менять список тестеров, не останавливать тестовый трек.
- Язык до входа определяется существующим региональным механизмом устройства; ручной выбор и язык аккаунта имеют приоритет. Исправлена обработка браузерного списка локалей без кода региона.
- Старый сайт остаётся функциональным до проверки нового сайта, Google OAuth и синхронизации Android. Объявление о переезде включается отдельно и только после этих проверок.

## Порядок переключения без двух независимо изменяемых баз

1. Проверить SSH, HTTPS, PHP 8.3 и расширения на Hostinger. Подготовить проверенный код из Git и подписанную сборку workflow `prepare-relocation.yml`; секретов в артефакте нет.
2. Установить на старом хосте отслеживаемые обработчик `server/src/relocation.php`, роутер API и cron с проверкой маркера. Без маркера поведение прежнее.
3. Подготовить новый закрытый server-каталог и конфигурацию, сохранив прежний `crypto_key`, Google OAuth и остальные нужные параметры. Новый API держать в режиме обслуживания до финальной копии.
4. На старом хосте атомарно создать `server/var/relocation.json` с `mode=freeze`. Это останавливает API до открытия БД и пропускает старый cron. Дождаться завершения уже начатых запросов и фонового cron. Создать согласованную копию через `ops/backup-runtime.php`, проверить `integrity_check`, передать БД и сессии по SSH.
5. На новом хосте проверить целостность, количество записей и расшифровку токенов без вывода содержимого. Убрать новый маркер обслуживания, проверить health, провайдеры и вход Google.
6. На старом хосте сменить маркер на `mode=forward`. Старые API-запросы передаются только на фиксированный HTTPS адрес genesiscalendar.com с прежними cookies/CSRF. Старая БД и cron больше не используются. Это сохраняет совместимость установленных APK и единственный источник записей на новом хосте.
7. Установить GitHub variable `GENESIS_DEPLOY_TARGET=hostinger`. Тот же `.github/workflows/deploy.yml` публикует новый production с преддеплойным runtime-бэкапом и обновляет на Beget только файлы совместимости и подписанный APK. Никаких секретов в Git.
8. После подтверждения Google OAuth-брендинга для `.com`, Google-входа и синхронизации нового Android-выпуска слить подготовленный redirect PR в `master`. Существующий workflow обновит `.htaccess` на Beget: страницы `.ru` и `www.genesiscalendar.ru` перенаправляются на фиксированный HTTPS-домен `.com` с сохранением пути и query; браузер сохраняет hash. Первоначально используется HTTP 302 с `Cache-Control: no-store`, чтобы откат не зависел от закешированного постоянного редиректа. API, downloads, Android update metadata, `.well-known` и существующие статические файлы остаются на старом origin. Новый runtime-маркер не требуется. До merge старый веб-интерфейс продолжает работать.
9. Cron запускается только на Hostinger каждые 5 минут. Старый cron безопасно пропускает выполнение при наличии маркера.

Откат до включения нового API: вернуть старый маркер в исходное отсутствующее состояние; исходная БД ещё не заменена. После начала записей на новом хосте сначала остановить API и cron там, создать согласованную копию, затем отдельно согласовать обратный перенос актуальных данных. Автоматически возвращать старую SQLite нельзя.

## Авторизация и совместимость

Google OAuth использует тот же web client, Android package и сертификат. В OAuth client разрешены оба origins и оба callback: `https://genesiscalendar.com/api/auth/google/callback` и прежний `.ru`. Proxy добавляет фиксированный заголовок прежнего origin: веб-вход, начатый на `.ru`, завершает callback на `.ru`, чтобы browser session/PKCE сохранились. Новый вход использует `.com`. Существующие Google-разрешения и refresh tokens переносим с прежним ключом шифрования. Новые OAuth clients, scopes и разрешения не создаются.

Нативный APK строится с `-PgenesisUrl=https://genesiscalendar.com/`. Android authorization хранится в независимом от домена контексте; старый формат читается для совместимости. В Play Console сохраняются приложение, package, подпись и текущий testing track/testers. Выпуск новой сборки в существующий трек выполняется после проверки; до этого старые версии продолжают обращаться через API proxy.

## Закрытые данные

На новом хосте config находится в `server/config.php`, SQLite в `server/var/genesis.sqlite`, PHP sessions в `server/var/sessions`. Никакой из этих файлов не должен попасть в `public_html`, Git, CI artifact или вывод команд. Сохраняются `crypto_key`, Google secrets и все исторические записи. Параметры Яндекса в новый config не переносятся. Наличие исторических записей не означает включённую поддержку Яндекса.

На старом хосте backup выполняет `/usr/local/php/cgi/8.3/bin/php ops/backup-runtime.php --server-root=/home/h/haiirodw/genesis-calendar/server --backup-root=/home/h/haiirodw/genesis-calendar/backups --retain=20`. На новом используется тот же helper и точный корень Hostinger. Он делает `VACUUM INTO`, проверяет целостность и сохраняет config. Переносится согласованная копия, а не live WAL.

## GitHub Actions

Существующий `.github/workflows/deploy.yml` сохраняется. GitHub variable `GENESIS_DEPLOY_TARGET=hostinger` выбирает новый host/origin, закрытый secret `HOSTINGER_SSH_KEY` даёт доступ только деплою. Перед публикацией: frozen install, lint, PHP syntax/native auth/relocation/backend tests, web tests, web build и подписанная Android сборка. Затем runtime backup, server/public deploy, health/SHA/APK checks и совместимые файлы на прежнем origin. Config и runtime исключены из rsync.

Первичная установка берёт отслеживаемый код из Git и portable artifact workflow `prepare-relocation.yml`; последующие обновления — только commit в рабочую ветку → push → merge master → Actions → проверка production. Полных копий отслеживаемого кода не создаём.

## Условия редиректа с .ru (решение пользователя 9 октября 2026)

- `/api/health` успешно отвечает, `/deploy-meta.json` содержит SHA master.
- Google web sign-in и callback успешно возвращают существующий аккаунт на `.com`; старый browser flow тоже работает.
- Перенесённые записи и шифрованные ключи/токены валидны, API старого origin использует новую базу.
- Подписанный APK/Play bundle использует `.com`, версия выше прежней, package/signature прежние; вход и синхронизация проверены на устройстве.
- Тестовый трек и список тестеров сохранены; установленные тестовые APK продолжают получать API и обновление.
- Новый OAuth-брендинг для `genesiscalendar.com` подтверждён в Google Verification Center; подтверждение только data access или владения доменом недостаточно.
- Только после всех проверок сливаем redirect PR. При обновлении старого service worker он снимает регистрацию и переводит открытые окна на `.com`, сохраняя путь, query и hash; локальные данные и кеши не удаляются. API proxy/обновления остаются для совместимости старых приложений. Старый домен и его настройки сохраняются.
- После Actions проверить 302 и Location для `/`, `/privacy`, `/terms` и SPA-пути с query; оба API health, выдачу Android update metadata и старые APK-ссылки. На `.com` не должно быть петли редиректов. `/deploy-meta.json` нового production должен соответствовать SHA master.
- Откат маршрутизации: revert redirect merge в `master`, дождаться существующего deploy workflow. Базу данных и маркер API-forward не менять.

Если Google-брендинг или проверка Google-входа/синхронизации нового Android-выпуска не подтверждены, redirect PR не сливать и явно записать непроверенные состояния в отчёт.

- Прежний закрытый Alpha 2.7.0 / 76 доступен выбранным тестерам; трек и группа из 12 человек сохранены.
- Прямой адрес старой оболочки `/legacy-home.php` тоже перенаправляется на главную `.com`. В совместимый artifact worker переезда копируется также под прежним именем `sw.js`: Beget отдаёт существующие JS-файлы через nginx, обходя Apache rewrite. Actions проверяет содержимое публичного worker, редирект с query и здоровье прежнего API. Регистрация worker использует `updateViaCache: "none"`, поэтому проверка обновлений не зависит от кеша старого JS-файла.
- `www.genesiscalendar.com` перенаправляется на основной адрес до входа. Сессионная cookie и Google callback используют один origin; путь и query сохраняются.
- Service worker не устанавливает HTML-ответ SPA fallback вместо JS/CSS-модуля и восстанавливает такие некорректные записи из сети. Это защищает уже открытые вкладки от ошибки ленивой загрузки после деплоя, сохраняя обычный offline cache и данные пользователя.
