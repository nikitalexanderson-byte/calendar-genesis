# Подготовка переноса GENESIS на другой хостинг и домен

Целевой адрес — `https://genesiscalendar.com`, Hostinger. Источник кода — `nikitalexanderson-byte/calendar-genesis`. Новый закрытый корень: `/home/u531952483/domains/genesiscalendar.com`; публичен только `public_html`. На Beget разрешён только прежний корень `/home/h/haiirodw/genesis-calendar`.

## Условия перехода 8 октября 2026

- На новом адресе доступен только вход Google. В закрытой конфигурации `google_only=true`; параметры Яндекса не переносятся. API Яндекса возвращает 404, кнопки входа и подключения скрыты, Метрика не загружается. Исторические данные не удаляются.
- Пакет Android `ru.genesis.calendar`, действующая подпись и тестовый трек сохраняются. Новая сборка 2.6.7 / 73 использует новый origin; локальный контекст шифрования авторизации уже независим от домена. Не менять список тестеров, не останавливать тестовый трек.
- Язык до входа определяется существующим региональным механизмом устройства; ручной выбор и язык аккаунта имеют приоритет. Исправлена обработка браузерного списка локалей без кода региона.
- Старый сайт остаётся функциональным до проверки нового сайта, Google OAuth и синхронизации Android. Объявление о переезде включается отдельно и только после этих проверок.

## Порядок переключения без двух независимо изменяемых баз

1. Проверить SSH, HTTPS, PHP 8.3 и расширения на Hostinger. Подготовить проверенный код из Git и подписанную сборку workflow `prepare-relocation.yml`; секретов в артефакте нет.
2. Установить на старом хосте отслеживаемые обработчик `server/src/relocation.php`, роутер API и cron с проверкой маркера. Без маркера поведение прежнее.
3. Подготовить новый закрытый server-каталог и конфигурацию, сохранив прежний `crypto_key`, Google OAuth и остальные нужные параметры. Новый API держать в режиме обслуживания до финальной копии.
4. На старом хосте атомарно создать `server/var/relocation.json` с `mode=freeze`. Это останавливает API до открытия БД и пропускает старый cron. Дождаться завершения уже начатых запросов и фонового cron. Создать согласованную копию через `ops/backup-runtime.php`, проверить `integrity_check`, передать БД и сессии по SSH.
5. На новом хосте проверить целостность, количество записей и расшифровку токенов без вывода содержимого. Убрать новый маркер обслуживания, проверить health, провайдеры и вход Google.
6. На старом хосте сменить маркер на `mode=forward`. Старые API-запросы передаются только на фиксированный HTTPS адрес genesiscalendar.com с прежними cookies/CSRF. Старая БД и cron больше не используются. Это сохраняет совместимость установленных APK и единственный источник записей на новом хосте.
7. Установить GitHub variable `GENESIS_DEPLOY_TARGET=hostinger`. Тот же `.github/workflows/deploy.yml` публикует новый production с преддеплойным runtime-бэкапом и обновляет на Beget только файлы совместимости и подписанный APK. Никаких секретов в Git.
8. После проверки Android, авторизации, синхронизации и сохранения текущего тестирования отдельно создать на Beget `server/var/legacy-announcement.json`. `.htaccess` показывает `relocated.html` со ссылкой; API совместимости и выдача обновления остаются доступны старым APK. До этого маркера старый веб-интерфейс не отключается.
9. Cron запускается только на Hostinger каждые 5 минут. Старый cron безопасно пропускает выполнение при наличии маркера.

Откат до включения нового API: вернуть старый маркер в исходное отсутствующее состояние; исходная БД ещё не заменена. После начала записей на новом хосте сначала остановить API и cron там, создать согласованную копию, затем отдельно согласовать обратный перенос актуальных данных. Автоматически возвращать старую SQLite нельзя.

## Что уже переносится без правки исходников

- Веб-сборка обращается к `/api` того же домена. Серверный `app_url` задаёт адрес OAuth callback для Google и Яндекса.
- Android APK собирается с `-PgenesisUrl=https://НОВЫЙ-ДОМЕН/`. С этим адресом работают API, проверка обновлений и ссылки в приложении. Имя пакета остаётся `ru.genesis.calendar`; для обновления установленного приложения требуется та же подпись и **больший `versionCode`**.
- Ручной workflow **Prepare GENESIS relocation package** собирает клиент, PHP API и подписанный APK для введённого HTTPS origin. Он выдаёт артефакт `genesis-relocation-package`, не подключается к новому хосту и не переключает DNS.

## Подготовка нового хоста

1. Выбрать домен и хост с HTTPS, PHP 8.3+, расширениями `pdo_sqlite`, `sodium`, `mbstring`, `curl`, `dom`, возможностью cron и записью в закрытый каталог для SQLite и сессий. Корень сайта должен указывать только на `public_html`; каталог `server` нельзя отдавать по HTTP.
2. Зарегистрировать новый HTTPS origin в настройках Google OAuth и Яндекс OAuth, включая `https://НОВЫЙ-ДОМЕН/api/auth/google/callback` и `https://НОВЫЙ-ДОМЕН/api/auth/yandex/callback`. Проверить разрешение Яндекс Календаря для OAuth-приложения. Если провайдер потребует новый client ID, обновить его только в закрытом `server/config.php` и секретах сборки Android. Старые client secrets в артефакт не входят.
3. В рабочей ветке поднять `versionCode` и `versionName` Android выше опубликованной версии. Запустить вручную **Prepare GENESIS relocation package**, указав новый origin без пути. Сохранить артефакт в защищённом месте; срок хранения артефакта в Actions — 7 дней.
4. Разместить `public_html` и `server` из артефакта в выбранном корне нового хоста. Создать закрытые `server/var` и `server/var/sessions` с правами процесса PHP. Из `server/config.example.php` создать `server/config.php` вне Git: установить новый `app_url`, абсолютные `db_path` и `session_path`, сохранить существующий `crypto_key` и нужные OAuth-настройки. Не отправлять config, ключ или БД в GitHub Actions artifact.

## Данные и переключение

1. Пока старый хост доступен, остановить изменяющие запросы и cron на время финальной копии. В **разрешённом корне GENESIS** на Beget использовать действующий `ops/backup-runtime.php`: он создаёт согласованную SQLite-копию и копию `config.php` в закрытом `backups/`. Перед передачей проверить `PRAGMA integrity_check` на копии. Не копировать напрямую работающий WAL-файл.
2. Передать копию БД и закрытую конфигурацию на новый хост по защищённому каналу. Проверить, что база содержит актуальные данные, а `crypto_key` совпадает со старым: иначе зашифрованные рабочие пространства, OAuth-токены и календарные подключения не откроются. Конфигурацию отредактировать под новый origin и пути. При необходимости перенести сессии отдельно; вход через Google или Яндекс после переноса остаётся штатным способом восстановления сессии.
3. Настроить HTTPS и маршрутизацию `/api/*` к `public_html/api/index.php` (на Apache используется приложенный `.htaccess`), затем запустить новый сайт на тестовом DNS/hosts. Проверить `/api/health`, `/deploy-meta.json`, `/android-update.json`, прямое скачивание APK, вход через оба провайдера, синхронизацию задач и Яндекс Календаря, а также Android APK с новым origin. Включить cron для `server/cron/sync.php` с новой конфигурацией; не запускать cron одновременно на двух хостах.
4. После успешных проверок переключить DNS или уведомить пользователей о новом домене. При сохранении старого домена временный HTTPS-редирект поможет веб-пользователям и старым версиям Android получить обновление. Если старый домен недоступен, приложение со старым встроенным адресом не сможет само найти новый хост: пользователям потребуется установить подписанный APK с нового домена. Это ограничение нельзя устранить, пока новый адрес неизвестен.

## Проверки и откат

- Сверить SHA из `deploy-meta.json` с собранным commit, код версии и SHA-256 APK с `android-update.json`, а `/api/health` — с `ok: true`.
- Проверить два сценария аккаунта: существующий Google и существующий Яндекс; для Яндекс Календаря отдельно проверить OAuth-доступ CalDAV, чтение и запись тестового события.
- При ошибке до DNS-переключения оставить прежний хост основным. После переключения остановить запись на новом хосте перед обратным переносом данных. Не восстанавливать SQLite поверх работающего сервиса и не выполнять автоматический откат БД.
- Бэкапы и конфигурацию хранить только в закрытых каталогах. Доступ к ним должен быть ограничен оператором сервиса.
