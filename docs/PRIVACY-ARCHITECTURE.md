# Приватная архитектура и модель доверия GENESIS

## Где находятся данные

| Данные | Устройство | Google Calendar | Google Tasks | Сервер GENESIS |
|---|---:|---:|---:|---:|
| Названия и описания календарных задач | Да | Да | Нет | Зашифрованный кэш синхронизации, Sodium secretbox |
| Названия списков и данные Google Tasks | Да | Нет | Да | Зашифрованный кэш синхронизации, Sodium secretbox |
| Даты, напоминания, повторения, статусы | Да | Да | Для нативных Google Tasks | Нет |
| Связи задач и теги | Да | В закрытых свойствах события | Нет | Нет |
| Проекты, подпроекты, привычки и трекеры | Да, рабочая offline-копия | В событиях задач только ссылки | Нет | AES-GCM ciphertext |
| Ключ рабочего пространства | Да, для offline-работы | Нет | Нет | Отдельно от ciphertext, зашифрован серверным ключом |
| Email, имя, аватар | Кэш профиля | Google Account | Google Account | Да, для аккаунта |
| OAuth refresh token | Нет | Выдаётся Google | Выдаётся Google | Да, Sodium secretbox |
| Пароль Google | Нет | Нет | Нет | Нет — вход выполняется на стороне Google OAuth |
| Статистика | Локально вычисляется | Нет | Нет | Только числовые агрегаты |

## Поток синхронизации

1. Пользователь входит через Google OAuth 2.0 с одноразовым `state` и PKCE; на этом этапе запрашиваются только `openid`, `email` и `profile`.
2. Пользователь отдельно подключает синхронизацию Calendar и Tasks и видит запрос соответствующих разрешений.
3. GENESIS создаёт отдельный календарь `GENESIS` с ограниченным scope `calendar.app.created`.
4. Календарная задача сразу сохраняется локально и отправляется как событие Google Calendar.
5. Списки и задачи Google Tasks читаются и изменяются через официальный API только после отдельного согласия.
6. ID проекта, теги, зависимости и статус находятся в `extendedProperties.private` события.
7. Структура проектов и данные трекеров сериализуются в JSON и шифруются в браузере Web Crypto AES-GCM до отправки на сервер.
8. Ключ рабочего пространства хранится на сервере отдельно, зашифрованным Sodium secretbox с ключом из закрытой серверной конфигурации.
9. После подтверждённого входа через Google защищённая серверная сессия получает ключ рабочего пространства, а браузер расшифровывает контейнер. Поэтому новое устройство открывает данные автоматически, без кода восстановления.
10. Без сети используется локальная рабочая копия и очередь изменений; при восстановлении связи изменения объединяются и отправляются на сервер.

Сервер проксирует события и задачи между приложением и Google API и хранит общий для устройств аккаунта кэш синхронизации в закрытом runtime-каталоге. Кэш зашифрован Sodium secretbox, разделён по основному/дополнительному аккаунту и действующим разрешениям Google. Открытое личное содержание не записывается в SQLite или административную статистику. При отключении сервисов, удалении дополнительного аккаунта или аккаунта GENESIS его кэш удаляется. OAuth-токены также зашифрованы Sodium secretbox.

Личные изменения отправляются в Google немедленно. Входящие изменения проверяются не чаще раза в 15 минут на аккаунт при активном использовании; полная сверка выполняется раз в сутки. Повторные запросы нескольких устройств читают один серверный кэш. Общие задачи, комментарии и подробности журнала хранятся в SQLite зашифрованными серверным ключом; даты, права, связи и статусы остаются индексируемыми метаданными. Общие данные передаются в Google только после включения пользователем синхронизации соответствующего проекта. Это защита при хранении, а не E2EE.

## Модель доверия

Текущая схема — это клиентское шифрование содержимого и защита данных при хранении, но **не zero-knowledge E2EE**. Серверное приложение с доступом к закрытому ключу конфигурации способно расшифровать ключ рабочего пространства. Это осознанный компромисс ради автоматического доступа после Google-входа на новом устройстве без отдельного пользовательского кода.

Устройство, профиль браузера и активная сессия пользователя считаются доверенными. Для offline-first работы браузер сохраняет в `localStorage` рабочую копию, очередь синхронизации и ключевой материал, привязанные к аккаунту. Импортированный Web Crypto ключ неэкспортируемый только во время криптографической операции; исходный ключ остаётся доступен коду приложения для следующего offline-запуска.

Модель защищает от чтения одного только ciphertext и от утечки одной только копии базы без закрытой серверной конфигурации. Она не защищает данные на уже разблокированном устройстве от:

- вредоносного расширения или XSS-кода с доступом к origin GENESIS;
- чтения профиля браузера или хранилища установленного PWA;
- компрометации активной сессии;
- одновременной компрометации production-сервера и его закрытого ключа конфигурации.

При удалении аккаунта серверные данные и локальная копия на текущем устройстве удаляются приложением. На остальных ранее использованных устройствах пользователь должен очистить данные сайта или установленного PWA. Обычный выход завершает серверную сессию и очищает ключ из памяти, но offline-данные устройства сохраняются для последующего входа; на общем устройстве после выхода следует очистить данные сайта.

## Возможное усиление

Если продукт вернётся к модели, в которой сервер принципиально не может восстановить ключ, потребуется отдельная модель восстановления или платформенное защищённое хранилище. Одного `CryptoKey` с флагом `extractable: false` недостаточно против XSS: код того же origin всё равно может использовать ключ для расшифровки. Такое изменение должно проектироваться вместе с переносом offline-кэша, восстановлением доступа и миграцией уже существующих аккаунтов.
