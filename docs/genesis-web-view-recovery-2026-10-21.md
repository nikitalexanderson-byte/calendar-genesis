# B5: устойчивое восстановление представлений в браузере

Аудит: прежние `genesis.shared-views.draft.<account>` и `.request` содержат незашифрованный ввод/запрос. `mutationId` заменяет ID при изменении тела после неизвестного результата. Кнопки редактирования/копирования/удаления остаются доступными после ошибки; reply проверяется лишь на editable definition, без всей исходной команды/revision. Ошибки записи localStorage не останавливают HTTPS. Поэтому существующий lost-reply happy path не доказывает сохранность при последующем редактировании, quota, malformed receipt или повторном отказе.

Выбран тот же один экран библиотеки/условий/результатов. Его уже подтверждённые блоки и icon actions сохраняются. Добавляется существующий компактный device-draft pattern; request identity блокирует замену/редактирование до подтверждённого результата. Применяются общие14-язычные подписи и44px icon controls, STANDART light/dark.

Используется account-global scope `00000000-0000-4000-8000-000000000005` и новый purpose `saved-views` существующего AES-GCM journal. Сначала durable command и attempt, затем HTTP. Успех проверяется по action/ID/revision/области/видимости/полному definition. Неизвестный результат и поздний отказ повторяют исходные bytes/requestId. Полученный receipt фиксируется до очистки или восстановления следующего собственного ввода. Ошибки чтения очищают server metadata/results/pickers.

Старые локальные draft/request импортируются до удаления plaintext. Request разбирается в исходный wire command, отмечается как уже попытанный и не получает нового ID. Если после старой неизвестной отправки пользователь успел изменить ввод, сохраняются и frozen command, и последующий ввод. Повреждённая исходная запись сохраняется для явного восстановления/выгрузки, не превращается в новый пустой фильтр. Удаление старых ключей выполняется только после успешной encrypted записи и сравнения исходных bytes.

До: `output/playwright/saved-view-before-*.png`. Новая native приёмка выполняется отдельно; этот browser срез не означает закрытия B5/C3 или основного промпта. Текущая цель — все этапы, проверки только на API28/API35; Realme отключён. SSH и production-БД не используются.

## Реализация и подтверждение

Legacy import использует отдельный writer, чтобы сохранить одновременно открытые черновики. Старые ключи удаляются после encrypted write и сравнения исходных bytes. Нажатие «Продолжить черновик» сначала сохраняет новую копию и только затем CAS-удаляет её источник. Command/attempt/receipt имеют отдельные фазы; попытанный неизвестный запрос не редактируется, не заменяется новым и не удаляется через UI. Изменение календаря ввода сохраняется только в local metadata и не меняет calendarMode/timeZone/yearStart относительного периода; новый черновик получает отдельный task-input mode.

384 web tests/i18n прошли, включая12 новых проверок writer/migration/receipt/independent input calendar. Frozen install, полный lint (0 ошибок/2 прежних img warnings) и build:beget прошли:90 entry/203 visual assets, max JS349993 bytes. Полный tsc всё ещё имеет10 исходных диагностик вне нового writer/экрана; он не объявляется успешным gate.

Настоящий browser/PHP flow подтвердил3 побайтно одинаковых create body (lost reply → reload →409 → replay), одну запись/revision1,2 одинаковых PATCH после malformed receipt и revision2,2 одинаковых DELETE после lost reply/reload и фактическое удаление. Повреждённое подтверждение не снимает блокировку; поздний409 не заменяет requestId. Названия и requestId отсутствуют в plaintext нового журнала, старые account-scoped plaintext keys удалены. Подтверждение — `output/view-durable-functional-confirm.log`.

Отдельный legacy/PHP сценарий подтвердил исходный requestId и единственную server revision1 при повреждённых bytes более позднего редактора. После получения receipt эти bytes остались отдельным собственным вводом, были выгружены через UI и не стали пустым/all-task фильтром (`output/view-durable-legacy-resume.log`). Первый setup этого harness ошибочно использовал `user.id` вместо `user.uid`; исправлен только тестовый namespace, повтор использовал тот же исходный запрос. Продуктовые данные этим setup не затрагивались.

Offline-проверка очищает task rows/counts, library и загруженные picker titles; свой ввод сохраняется локально, отправка недоступна, после подключения серверная выборка снова работает. Ошибки страниц/метаданных также очищают загруженные данные. Лог — `output/view-durable-offline.log`.

Сохранены16 initial и32 итоговых PNG: pending/recovery/damaged input/offline × обе схемы ×360/390/768/1440 (`output/playwright/view-durable-*.png`). В первом просмотре старые черновики отодвигали текущий повтор; одним пакетом они переведены в управляемый disclosure, дублирующее сообщение убрано. Контрольный lifecycle и16 captures прошли;8 damaged-input и8 offline проверяют новые состояния. Accessible names/44px, overflow и отсутствие смешивания календарей подтверждены. Просмотрены desktop/light и phone/dark originals. В тесте программные reload подавляют beforeunload, а удаление собственной fixture подтверждается harness; принудительный kill браузера этим не доказан.

Открыты новая реальная quota/storage race, два окна во время legacy import/CAS transfer, порча AES ciphertext и live revoke всего родительского workspace в этом browser harness. Общие storage/account/CAS механизмы имеют unit-покрытие, а server/native ACL проверены другими срезами; это не заменяет названные UI-сценарии. Отсутствующие до обновления bytes/старые уже перезаписанные requestId не восстанавливаются выдуманным запросом. Native cross-project bulk и следующие G/C/B-интеграции продолжаются.
