# Миграция 086: задачи только внутри проектов

## Поведение и совместимость

`086_shared_project_inboxes.sql` применяется один раз штатным загрузчиком миграций, в транзакции вместе с записью `schema_migrations`. Исторический проект `is_inbox=1` остаётся для членства и старых маршрутов, но больше не является контейнером новых задач.

Для каждого проекта добавляется пара внутренних статусов `chaos-open:<id>` / `chaos-done:<id>`, помеченная `is_chaos=1`. Она сохраняет существующий NOT NULL FK `status_id`, но не входит в доски, их лимит 30, настройки статусов и варианты workflow. Пустое назначение доски означает хаос-бокс проекта. Завершение/повторное открытие сохраняет размещение в нём. Экспорт/импорт передаёт `isChaos` отдельно от видимых досок; старые файлы без него читаются с `false`.

Существующие задачи корня перемещаются в первый активный, не удалённый проект того же пространства по `created_at,id`. При отсутствии проекта создаётся `recovered-project:<spaceId>` («Перенесённые задачи») с аудиторией и ролями прежнего inbox. ACL существующего проекта не расширяется: доступ после переноса определяется его текущими правами. Верхние списки задач переподчиняются выбранному проекту вне доски.

ID задач и шифрованное содержимое не меняются; сохраняются комментарии, связи, значения полей, контрольные списки, архив/корзина и завершённость. Revision и updated_at меняются для инвалидирования старого состояния. Привязанные категории/поля перемещаются вместе с задачами. Перенесённое проектное поле становится необязательным, чтобы не блокировать уже существующие задачи назначения; прежнее `required` записано в журнале. Глобальные поля пространства не меняются.

Повторения получают новый проект; старое назначение из сохранённого шифрованного шаблона разрешается через журнал при генерации, без переписывания шаблона. Старые Google-проекции ставятся в существующую очередь удаления с прежними user/destination/list ID; исходные связи затем снимаются. Новая проекция подчиняется настройкам и доступу проекта назначения.

API отклоняет создание/перенос задач и создание списков в корень. DB-триггеры дополнительно запрещают INSERT/UPDATE задач в `is_inbox=1`, защищая от старых клиентов и обходных путей. Успешные прежние receipts воспроизводятся до новых проверок, сохраняя идемпотентность. Неотправленные старые offline-команды в корень будут отклонены; их локальные черновики не удаляются автоматически.

Код хранится в Git. Не добавлять полную копию сайта или ручную правку production-БД.

Изолированный тест воспроизводит миграцию на populated pre-086 schema, предварительно делает `VACUUM INTO`, проверяет неизменность резервной копии, FK, исходных шифротекстов и связей. При ошибке SQL транзакция загрузчика откатывается целиком. Если нет подтверждённой runtime-копии или CI завершился неуспешно, выпуск не продолжать.

После деплоя проверить SHA в `/deploy-meta.json`, `/api/health`, отсутствие задач в корне, размещение задач по журналу, отсутствие внутренних статусов среди досок, создание/перенос/завершение задачи в хаос-боксе и работу очереди Google cleanup. В эту подготовку production-проверки не входят.

## Восстановление

Автоматического database rollback нет. `git revert` возвращает код, но не прежнее размещение данных и не удаляет колонку/журналы/триггеры. Старый сервер может показать внутренние статусы как доски и получить отказ на запись в старый inbox; для частичного отката интерфейса предпочтителен корректирующий commit с сохранением фильтрации и новых ограничений.

Для полного отката данных отдельно остановить writers/workers, проверить созданную непосредственно перед выпуском runtime-копию и согласовать восстановление. Таблицы `shared_workspace_inbox_relocations`, `shared_workspace_task_relocations`, `shared_workspace_list_relocations`, `shared_workspace_scope_relocations` содержат прежние контейнеры, статусы, revision/updated_at и required. Они пригодны для сверки и плана адресного восстановления, но не для слепого обратного UPDATE после новых пользовательских изменений. Возврат в корень конфликтует с новыми триггерами и требует отдельного согласованного сценария; удалённые Google-копии могут потребовать повторной синхронизации. Не удалять recovery-проект или новые задачи при откате кода.
