# G3: workflow/WIP — сервер и первый веб-экран

Основание: master629ba5d, после приоритетных UI-просьб пользователя и успешного PR #200. Серверный checkpoint d78b5b2 сохранён до UI-выпуска и затем объединён со свежим master. G3 реализуется отдельно от protocol7/E4/F. Простые проекты сохраняют прежнее поведение; расширенный workflow включается явно в настройках одного существующего проекта.

Единственный контракт: правила статусов с WIP и обязательными полями, разрешённые переходы (включая создание), текущие проектные роли. Повторное утверждение результата не вводится: используются существующие approvers/children checks. Настройка хранится зашифрованно с ревизиями, историей и CAS/receipt; права проверяются перед replay. Владелец должен иметь путь из каждого незавершённого статуса к завершённому. Включение/ужесточение проверяет существующие активные задачи и WIP под SQLite writer lock; статусы нельзя семантически менять/удалять при включённом workflow, пока его явно не отключат. Нули и false пользовательских полей считаются заполненными.

Общие серверные guards вызываются после нормализации фактических task/custom/planning values, внутри существующей write transaction. Отдельно покрываются task create/edit, move, approval, unarchive/trash/project restore и исторический C5 import. Bulk/C1/C2/series используют те же guards; audit hook не используется как единственная защита. C5 строит граф во временных open-статусах: workflow проверяет реальные конечные статусы, entry-роли, поля и WIP после archived metadata, до commit. Существующие ACL/approvals/children checks во время staging сохраняются. Архив и корзина освобождают WIP; восстановление снова проверяет поля и вместимость. Настройка остаётся доступной текущему управляющему в архиве/корзине, чтобы можно было безопасно исправить конфигурацию перед восстановлением.

Сначала сервер/миграция/поведенческие проверки, затем один экран настройки в существующем планировании и понятные ошибки в текущих task flows,14 языков и две темы×4 ширины. G3 остаётся открытым до native и всех зависимых сценариев.078 аддитивна; штатный CI-backup сохраняется. Code rollback не удаляет definitions/history; автоматического восстановления БД нет. Старые клиенты на новом сервере получают те же ограничения, даже если не знают новых настроек. Проверка старого сервера после rollback и все непроверенные состояния будут записаны по результатам миграционных тестов.

Реализованы GET/PUT `/shared/projects/:id/workflow` и GET history с пагинацией50 версий. Snapshot проекта содержит opt-in workflow; workspace protocol6 сохраняется. Включение проверяет текущие активные задачи, поля и вместимость; запрещённые изменения откатывают всю транзакцию вместе с audit/notifications/receipts. Ролевое условие не выдаёт базовых прав. Ошибки несут WORKFLOW-код и безопасные детали (статус, лимит, недостающие поля), которые объясняются в задачах, bulk, C1/C2/C3/C5 и планировании. Существующее утверждение результата остаётся единственным approval-процессом.

В существующем окне «Планирование» добавлен сворачиваемый блок «Процесс и лимиты»; он работает независимо от включения спринтов. Данные загружаются только после раскрытия блока. Управляющий видит лимиты и обязательные core/C3/G2-поля по статусам, разрешённые переходы отдельно для входа в проект и каждого исходного статуса, роли, текущие количества и историю версий. Редактор сохраняет черновик при CAS-конфликте и смене языка, предлагает явный перенос на актуальную версию; потерянный committed response повторяется с тем же requestId. Читатель видит настройки без кнопок изменения. После отключения правил возвращается прежняя семантика проекта. Используется существующий Universal UI, без смены стека, ассетов или UI-библиотеки.

Расширенная серверная приёмка проверила13 групп: opt-in/ACL/CAS/replay/history; transitions/roles/required/0/false/WIP/rollback; status/field safety; atomic approval; archive/trash restore; encrypted repair/revoke; два реальных PHP-процесса при WIP1 (один успех/один отказ); bulk с1 успехом/1 пропуском и точным кодом; C1 entry и rollback первого созданного task после отказа второго; перенос между проектами; реальную C2 background queue с failed-кодом и откатом эффектов; C5 окончательные entry/WIP/archive и rollback staged graph; полноценное редактирование правил проекта в корзине перед guarded restore. Исправлен доступ к scoped C3 definitions в корзине: обычный C3 reader намеренно скрывает удалённые проекты, workflow проверяет текущий manage-доступ и читает только определения нужного пространства/проекта.
