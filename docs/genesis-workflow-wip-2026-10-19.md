# G3: workflow/WIP — решение перед реализацией

Основание: master6f3f744, после приоритетных UI-просьб пользователя. G3 реализуется отдельно от protocol7/E4/F. Простые проекты сохраняют прежнее поведение; расширенный workflow включается явно в настройках одного существующего проекта.

Единственный контракт: правила статусов с WIP и обязательными полями, разрешённые переходы (включая создание), текущие проектные роли. Повторное утверждение результата не вводится: используются существующие approvers/children checks. Настройка хранится зашифрованно с ревизиями, историей и CAS/receipt; права проверяются перед replay. Владелец должен иметь путь из каждого незавершённого статуса к завершённому. Включение/ужесточение проверяет существующие активные задачи и WIP под SQLite writer lock; статусы нельзя семантически менять/удалять при включённом workflow, пока его явно не отключат. Нули и false пользовательских полей считаются заполненными.

Общие серверные guards вызываются после нормализации фактических task/custom/planning values, внутри существующей write transaction. Отдельно покрываются task create/edit, move, approval, unarchive/trash/project restore и исторический C5 import. Bulk/C1/C2/series используют те же guards; audit hook не используется как единственная защита. C5 строит граф во временных open-статусах: workflow проверяет реальные конечные статусы, entry-роли, поля и WIP после archived metadata, до commit. Существующие ACL/approvals/children checks во время staging сохраняются. Архив и корзина освобождают WIP; восстановление снова проверяет поля и вместимость. Настройка остаётся доступной текущему управляющему в архиве/корзине, чтобы можно было безопасно исправить конфигурацию перед восстановлением.

Сначала сервер/миграция/поведенческие проверки, затем один экран настройки в существующем планировании и понятные ошибки в текущих task flows,14 языков и две темы×4 ширины. G3 остаётся открытым до native и всех зависимых сценариев.078 аддитивна; штатный CI-backup сохраняется. Code rollback не удаляет definitions/history; автоматического восстановления БД нет. Старые клиенты на новом сервере получают те же ограничения, даже если не знают новых настроек. Проверка старого сервера после rollback и все непроверенные состояния будут записаны по результатам миграционных тестов.
